# Épica 15 — Revisión de seguridad (Instrucciones.md §80)

Estado: **en progreso** (2026-09-21) — primera pasada real. No se marca "completa": el rollout de App Check queda bloqueado en configuración externa que solo el usuario puede hacer (ver abajo), y una revisión completa de seguridad es, por naturaleza, algo a repetir antes de cada release (Épica 17), no un checklist que se tacha una sola vez.

## Hallazgo real y arreglado: `firestore.rules` permitía falsificar `subscription.isPremium`

La regla original de `users/{userId}` era `allow read, write: if request.auth.uid == userId` — sin restricción de qué campos podía escribir el cliente. Eso significaba que, aunque ningún código de la app escribe hoy un campo `subscription`, un cliente manipulado (Firestore SDK/REST directo, sin pasar por la UI de la app) SÍ podía escribir `users/{propio uid}.subscription.isPremium = true` directamente. Varias Cloud Functions (`fetchMinimalProfile` en `ai/askNutritionAssistant.ts`, `fetchOnboardingProfile` en `plan/adjustDailyPlan.ts`, y el mismo patrón en `plan/generateDailyPlan.ts`) leen ese campo como fuente de verdad para decidir límites de cuota — exactamente lo que Instrucciones.md §70 ("DO NOT TRUST CLIENT-SIDE PREMIUM STATUS") y §25 ("Never trust: subscription status supplied by the client") piden evitar. El código de las Cloud Functions en sí nunca confía en nada que el cliente mande en el PAYLOAD de la llamada — pero si el cliente puede escribir el campo directo en Firestore, el resultado es el mismo hueco por otra puerta.

**Arreglo**: `firestore.rules` ahora separa `create`/`update`/`delete` y usa un allowlist explícito de campos —`onboarding`, `onboardingCompletedAt`, `notificationPreferences` (los únicos que el cliente escribe hoy, confirmado grepeando `lib/` por escrituras a `users/{uid}`). El `update` usa `request.resource.data.diff(resource.data).affectedKeys().hasOnly([...])` en vez de `request.resource.data.keys().hasOnly([...])` — la diferencia importa: con `SetOptions(merge:true)`, `.keys()` refleja el documento COMPLETO resultante (incluyendo campos que esta escritura ni toca, como un futuro `subscription` escrito por Admin SDK), así que un `hasOnly` sobre `.keys()` se habría roto en cuanto la Épica 13 empezara a escribir ese campo. `diff().affectedKeys()` en cambio solo mira lo que ESTA escritura cambia — el cliente queda bloqueado de tocar `subscription` para siempre, sin importar qué otros campos existan en el documento. `delete` se bloqueó del todo (`deleteAccount`, Épica 11, usa el Admin SDK, que ignora estas reglas de todos modos).

No desplegado todavía (mismo estado que el resto de `firestore.rules`/`storage.rules`/`functions/` — ver "Open questions" en `TASKS.md`), pero corregido en el código antes de que la Épica 13 (que sí escribiría `subscription`) hiciera el hueco explotable en producción.

## Revisado, sin cambios necesarios

- **`storage.rules`** (Épica 8) — ya restringe por `userId`, tamaño (10 MB) y `contentType`. Sin hallazgos.
- **Validación de entrada en Cloud Functions** — revisadas `askNutritionAssistant`, `adjustDailyPlan`, `replaceMeal`, `registerMeal`: todas validan `request.auth`, longitud de texto libre (`MAX_QUESTION_LENGTH`/`MAX_MESSAGE_LENGTH`), y cualquier índice/id que llega del cliente (`mealId`, `candidateIndex`) se resuelve contra datos ya existentes del propio usuario en Firestore — nunca se confía en contenido que el cliente diga que es "la comida X" sin verificarlo primero contra el documento real.
- **Cuota de IA (`ai/quota.ts`)** — transacción atómica de Firestore correcta: lee, valida contra el límite, e incrementa dentro de la misma `runTransaction`, así que dos llamadas simultáneas no pueden ambas pasar el chequeo y quedar por debajo del límite real. `refundAiQuota` es best-effort y falla seguro (en el peor caso el usuario pierde una consulta que le tocaba, nunca gana una de más).
- **`functions/` — dependencias (`npm audit`)**: 2 vulnerabilidades moderadas transitivas (`uuid` <11.1.1, vía `gaxios`, a su vez vía `googleapis`/`firebase-admin`) — "missing buffer bounds check cuando se provee un buffer propio a `uuid.v3/v5/v6`". `npm audit fix` (sin `--force`) no resuelve nada: el fix real necesitaría subir de versión mayor `googleapis`/`firebase-admin`, sin poder probar el resultado en este entorno (sin deploy). El código de este proyecto nunca llama a `uuid` directo ni le pasa un buffer propio — es una dependencia transitiva de bajo riesgo real aquí. **Decisión**: no forzar el upgrade a ciegas; revisar cuando `firebase-admin` se actualice por otra razón, o antes de la Épica 17 (release).

## Pendiente — App Check (bloqueado en configuración externa)

Instrucciones.md §24: usar Firebase App Check para proteger las Cloud Functions/Storage de clientes no oficiales (nunca como única capa — el resto de esta revisión sigue aplicando igual). `firebase_app_check` ya es una dependencia declarada desde la Épica 1, sin activar todavía. Activar la ENFORCEMENT (`enforceAppCheck: true` en cada Cloud Function) sin que el cliente ya mande tokens válidos rechazaría TODO tráfico real en cuanto se despliegue — así que esto necesita, en este orden:

1. El usuario registra un proveedor real en la consola de Firebase/Google Cloud: reCAPTCHA v3 (o Enterprise) para Web, Play Integrity para Android, App Attest/DeviceCheck para iOS — nada de esto es algo que a esta sesión le sea posible generar (necesita acceso a esas consolas).
2. El cliente Flutter activa `FirebaseAppCheck.instance.activate(...)` con esos providers reales.
3. Recién ahí, cada Cloud Function pasa a `enforceAppCheck: true`.

Por qué esto quedó fuera de esta pasada en vez de dejar un scaffold a medias: activar App Check en el cliente con una site key de relleno es código muerto hasta tener la real, y el verdadero valor de seguridad (protección real de endpoints "gratis" como `registerMeal`, que no tienen cuota de IA que los frene) solo llega con el paso 3 — que sería peligroso activar sin poder probar en un dispositivo real que el cliente ya manda tokens válidos. Se le preguntó al usuario cómo prefiere proceder (ver el mensaje de esta tarea).
